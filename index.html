01

The problem

South Africa has roughly 150,000 spaza shops, contributing about 5.2% of GDP and supporting an estimated 2.6 million livelihoods. Informal retail makes up around 30% of the country's total retail market, and 40–50% of grocery sales in township communities specifically.

Despite that scale, close to nine in ten transactions in the informal sector are still cash. Existing digital options tend to bring high transaction costs, expensive hardware, or systems that don't work across different providers.

02

The solution

The solution is built around a short-lived, single-use payment code. A buyer generates the code in advance and writes it on a note that can be carried to the shop by someone else. The code can remain valid for up to around 10 minutes, but it expires immediately after a successful payment.

The 10-minute window is useful for the everyday scenario we want to enable: a parent can generate a code at home and send a child to the corner shop to buy bread — without giving the child a phone, cash, or access to the buyer's account. If the note is lost or intercepted, its usefulness is limited by the short expiry window, and once it has been accepted once, it cannot be reused.

Step 1 — setup, once

Buyer and our server agree on a shared secret while the buyer has signal.

Step 2 — offline

The app derives a code from the secret, the current time and transaction inputs. No connectivity needed.

Step 3 — at the till

Seller relays {code, amount}. The server verifies, marks it spent, and settles via Open Payments.

HMAC( secret , time_window ) → truncate → 6 digits  ·  verifiable server-side without the buyer ever being online

The app applies a cryptographic hash or keyed hash function to those values, producing a short code that the server can independently verify without the buyer needing connectivity. The seller enters the code and the purchase amount into the seller app, which forwards them to our server. The server checks that the code is authentic, still within its validity window, and has not already been spent. If those checks pass, it marks the code as used and continues with the Open Payments flow.

This shared-secret, offline-generation model is what powers the buyer-side offline experience: the buyer does not need signal at the moment the code is created or handed over. The seller and our server still need connectivity to submit and settle the transaction — but the person making the payment can prepare it entirely offline.

See it run. The Live demo tab has two working phones — a buyer app generating a real HMAC code offline, and a seller till relaying it to the server. Write a note, carry it across, and try to spend it twice.

03

How this addresses the brief

The challenge brief lists eight things a solution might explore. Here's where we land on each.

✓ Low-cost digital payment acceptance

The code itself is just a short cryptographic calculation: the app computes HMAC(secret, time window) and truncates the result to a few digits. 10MB costing R2 across 1,000 transactions is R0.002 per transaction.

✓ Payments without expensive point-of-sale hardware

Sellers only need a phone with data and our app; no card reader, NFC terminal, or dedicated hardware. Many low-budget phones don't have NFC — and a phone that can run an app or send data is not automatically NFC-capable. Our design works on ordinary connected phones.

✓ Interoperability between wallets/providers

This is what Open Payments buys directly: any wallet address works, regardless of which provider issued it. No closed-loop lock-in.

✓ Faster or more transparent settlement

Sub-second answer at the till, settlement a beat behind — and a plain running record of amount, timestamp and seller the shop can check whenever it likes.

✓ Offline or low-connectivity payment experiences

Our core differentiator: the buyer never needs signal — or even a phone — at the moment of purchase.

✓ Simple onboarding for shop owners

A seller needs three things: a phone with data, an Open Payments wallet address (sign up with any supporting provider), and our app. No merchant bank account application, no hardware order, no card-scheme approval.

✓ Better transaction records and payment visibility

Every transaction is logged server-side with amount, timestamp and seller — a plain running record the seller can check.

— Customer loyalty / community features

Deliberately out of scope, in line with the brief's own "you don't need to solve everything." Worth noting for the pitch though: the same grant mechanism extends naturally to stokvel-style pooled contributions. Good v2 material, not core scope.

04

How Open Payments actually works

Open Payments is an open API standard that banks, mobile money providers, and digital wallets can implement so third-party apps (like ours) can initiate payments on a user's behalf, with their consent, without ever touching raw banking credentials. It's built from three pieces:

Wallet address server

Exposes public info about an account via a "wallet address" — a URL-based version of an email address, e.g. $wallet.example/alice.

Resource server

The API for actually doing things against an account: creating quotes, incoming payments, outgoing payments.

Authorization server

Issues grants (permission slips) that let a client call the resource server, using the GNAP standard.

A payment happens in three steps

01

Incoming payment, created on the seller's side — "expect a payment of this amount." Grant for this is non-interactive.

02

Quote, created on the buyer's side — calculates exactly how much leaves the buyer's account, how much the seller receives, and the routing/conversion in between. Also non-interactive.

03

Outgoing payment, created on the buyer's side — actually moves the money. Open Payments requires this grant to be interactive: the buyer has to explicitly consent, via their own wallet's own consent screen, before a token is issued.

That third step is the one that matters most for our design.

How we use it

Step 3 is the only place Open Payments requires the buyer to be interactively present — so that's the one moment, at registration, where the buyer is online and consents directly, through their wallet's own screen, to a grant scoped the way subscriptions are: something like "up to R50 per transaction, R500 a month, through this app." After that, our server can create quotes and outgoing payments against that standing grant without asking the buyer to interact again — no redirect, no re-prompt, per purchase.

Once, at registration

  • Buyer consents via their wallet's own screen
  • Grant bounded: R50/txn, R500/month
  • Shared secret registered with our server

Every purchase after

  • Code derived offline from secret + time
  • Single-use: spent the instant it's accepted
  • No redirect, no re-prompt, no buyer interaction

We dropped the hash-chained ledger idea from an earlier draft. With Open Payments as the actual settlement rail, the record of truth lives with the wallet providers — a bespoke tamper-evidence layer on our own database added complexity without adding to what's actually being judged. That time is better spent on the Open Payments integration itself, which is 20% of the judging criteria on its own.

For building this: Interledger runs a free test wallet network at wallet.interledger-test.dev — sign up, get a key pair, and you've got sender and receiver wallets to build and demo against without needing a real bank relationship.

06

How we keep it fast

Two things do the work:

01

The slow part happens once, not per purchase

The interactive grant — the only step in Open Payments that needs the buyer present — is done at registration. Everything after runs against the standing grant: no redirect, no re-prompt.

02

Fast local answer; settle a beat behind

Our server verifies the code and checks a recently-synced balance snapshot in milliseconds — enough to give the seller an instant approval. The actual Open Payments call runs asynchronously right after.

This is exactly how contactless card payments already work: the terminal shows green before the transaction has technically cleared. It does reopen a sliver of the double-spend exposure we solved earlier, so it stays bounded by the same per-transaction and monthly caps as before.

Realistic target: sub-second for the "can I have my bread and coke" answer at the till; a few seconds behind that for settlement to actually land.

07

Is offline actually solved?

For the buyer's side, yes — nothing about the Open Payments pivot touches that. The code is still generated from a locally-held secret and the current time, no signal required, and the note-and-messenger flow is unchanged.

What was never offline, and still isn't, is the seller and the server — the seller's device needs connectivity to relay the transaction and reach Open Payments, exactly the requirement we had before this pivot.

Worth being precise about that boundary in the pitch: it's the buyer-side experience that's offline-first, not the system end to end. That's still a strong, differentiated claim — most existing options require both sides to be online and equipped — but it isn't "works with no internet anywhere," and a sharp judge may probe exactly that line.

Either way, seller-side data cost is a rounding error next to the value of a single sale. The bigger cost story is what Interledger is actually built to fix: the challenge brief itself notes that remittances into the region average around 12.7% in fees, against a G20 target of 3% — the kind of cost ILP exists to route around, by moving value between ledgers directly instead of through several intermediaries each taking a cut.

We don't have a verified fee figure for a spaza-shop-scale domestic transaction specifically, so the honest framing is "inherits the low-cost design goal of the rail it's built on," not a specific percentage we haven't confirmed.

09

Where the simplicity lives

Everything genuinely complicated — grants, quotes, wallet addresses, atomic balance checks — sits on our side and the wallet providers' side. The buyer never sees any of it: write a code, hand it to someone, done. The seller's experience: type a code and an amount, get a yes or no.

That gap between "sophisticated backend" and "trivial front-of-house interaction" is worth stating outright in the pitch — it's the direct answer to the UX & Accessibility and simple-onboarding parts of the brief, and it's true specifically because the complexity got pushed into a one-time setup step instead of every transaction.

Open questions

→

Exact grant scoping — the precise API shape for a recurring/limited outgoing-payment grant (interval, cap) needs confirming against the Open Payments docs or the hackathon Slack mentors; we're confident the pattern exists (subscriptions are a first-class use case) but haven't pinned the exact request shape.

→

SMS vs. data for the seller-to-server leg — leaning data for the build; SMS/USSD is a strong "scales to feature-phone merchants" talking point, precedented by M-Pesa, probably a slide rather than working code this weekend.

→

Async settlement risk window — needs a concrete cap number before demo day, not just "small."
