Offline authorization · connected settlement

Pay when the payer is offline.

Atomic Commits lets a payer generate a short-lived payment code without a live connection. A participating merchant submits that code, the amount and their wallet address; Atomic Commits verifies it and settles through Open Payments using permission the payer approved during onboarding.

What “standing permission” means

The payer does not approve every shop or every payment.

During setup

Atomic Commits requests an interactive Open Payments outgoing-payment grant. The payer is redirected to their provider and explicitly approves a spending limit, for example R500 per month.

After approval

Atomic Commits receives an access token tied to that grant. While it remains valid and within its limit, the app can create outgoing payments without asking the payer to approve each one again.

At the shop

The merchant is not pre-selected. When a valid offline code is redeemed, the merchant's wallet becomes the recipient for that transaction.

Two different limits

Open Payments controls the wallet permission. Atomic Commits controls each offline code.

Open Payments

Example: allow Atomic Commits to debit up to R500 in the current monthly interval.

Atomic Commits

Example: max R50 per offline authorization, valid for 10 or 30 minutes, single use, rate-limited verification.

Why split them?

The user consents to the broad wallet permission once. Our app can enforce stricter rules without pretending those per-code rules are native Open Payments grant fields.

Changing a local per-code limit can stay inside Atomic Commits. Increasing the underlying Open Payments grant would require the appropriate consent flow again.

One setup, many merchants

Payer registers with Atomic Commits

The payer device and Atomic Commits server establish the shared secret used to verify future offline codes.

02

The short payer ID selects the right secret

When a merchant submits 7K3M 482193, the server uses 7K3M to locate that payer's verification record. It does not search every user's secret.

03

The merchant supplies the recipient wallet

The payer did not need to know or pair with that shop in advance. The merchant includes its own wallet address when redeeming the code.

04

Atomic Commits verifies before payment

The server checks authenticity, validity window, replay state and the app's transaction policy, then uses the existing Open Payments grant to execute the transfer.

Implementation notes

What the short code actually proves.

The human code is intentionally small. The payer ID provides the namespace; the time-derived value provides the offline proof; the server provides replay protection and policy enforcement.

Code derivation

The payer and server share a secret established during setup. The device can therefore derive a code with no network request.

Validity without server-minted codes

The code is still generated locally. The server changes how many recent 5-minute windows it is willing to accept.

ROTATIONThe payer derives a fresh display code every 5 minutes. No server request is needed to generate it.
30 MIN MAXThe verifier checks the current 5-minute window and the previous five. Because rotation happens on fixed boundaries, any one code lives for about 25–30 minutes.
REDEEMOnce a matching code is accepted, claim it in a uniqueness-constrained record before attempting payment.
REPLAYA later attempt using the same payer ID + code is rejected as already spent.
The 15-second rotation in the sandbox only makes the mechanism visible during a demo. Production timing would use the 5-minute windows above.
