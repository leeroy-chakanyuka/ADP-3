Why “Atomic Commits”?

Every payment is a commitment.

In software, a commit is a deliberate state change. Here, a payment authorization is bounded, single-use and claimed once.

01

Onboard once while connected

The payer authorizes Atomic Commits through their Open Payments provider and the payer device establishes its shared secret with our server.

02

Generate locally later

The payer ID tells the server which secret to verify against. The six-digit value is derived locally from that secret and the current time epoch.

03

Merchant supplies the destination

The shop submits the payer ID, short code, amount and its own wallet address. There is no payer↔merchant secret and no prior pairing between them.

04

Verify, claim once, then pay

Atomic Commits verifies the code, atomically claims the authorization as single-use, checks its policy, then performs the payment through Open Payments.

Technical shape

Small code.
Clear boundaries.

We are deliberately keeping the offline primitive boring: time-derived HMAC-style verification, a payer namespace, a short acceptance window, server-side replay protection, and a separate Open Payments settlement layer.

Offline authorization

The human-facing code stays short because the payer alias identifies which account secret should be checked.

payer = 7K3M epoch = floor(time / 5 min) otp = truncate( HMAC(secret, payer + epoch) ) merchant sends: { payer, otp, amount, wallet }

10 or 30 minutes without server minting

The payer still generates the code offline. The verifier simply accepts a bounded number of recent five-minute epochs.

10 min → current + 1 recent epoch 30 min → current + 5 recent epochs then: verify authenticity check amount ≤ R50 claim code once execute payment
Payer namespace

Solves the “which secret do I verify?” problem without making the merchant pair with each customer.

Six-digit OTP

Human-transferable and deliberately small; guessing is constrained with expiry, per-payer rate limiting and transaction limits.

Atomic claim

The authorization changes from unused to claimed once. Two concurrent redemption attempts cannot both win.

Open Payments

Handles interoperable money movement. Atomic Commits is the authorization and policy layer in front of it.

Offline boundary

The payer can be offline. The merchant and Atomic Commits server still need connectivity in the current design.

The point

Digital payments that survive the last mile.

The innovation is not “writing a payment code on paper.” Paper is just one carrier. The useful primitive is a portable, constrained authorization that the payer can create without a live connection and that any participating merchant can redeem without prior pairing.

That lets Atomic Commits keep the user journey small: authorize the platform once, then use the same relationship across the merchant network.

Every payment is a commitment. Atomic Commits makes that commitment bounded, single-use and explicit.
